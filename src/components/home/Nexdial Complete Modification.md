============================================================ 1.
NON-NEGOTIABLE DESIGN PRESERVATION RULES
============================================================

The owner explicitly likes the current visual design. This task is a
content, messaging, conversion, trust, functionality, and SEO
improvement—not a redesign.

DO NOT change: - Existing brand colours, including current dark
background, text colours, accent colours, borders, or gradients. -
Existing font families, font weights, typography scale, or text styling
system unless a minor accessibility correction is essential. - Existing
animations, animation timing, motion effects, transitions, hover
effects, and reveal effects. - Existing cards, card design, card radius,
card shadows, card borders, card spacing, and card hover behaviour. -
Existing page layout, section layout, grid systems, responsive design
language, button styling, navigation style, header, footer, or visual
identity unless a content change cannot be implemented otherwise. -
Existing visual assets, logo, icon style, or decorative elements unless
they are broken or clearly inaccurate. - Existing framework, deployment
setup, or working components without a demonstrated need. - Any existing
working functionality that is unrelated to this PRD.

Allowed: - Change wording, headings, service descriptions, CTA labels,
metadata, SEO text, form fields, project case-study content, FAQs, and
explanatory content. - Reorder or remove misleading content sections
while preserving their visual styling and component design. - Replace
CRM/SaaS/product messaging with data-service messaging where
appropriate. - Add content within existing cards and section patterns. -
Add new service or case-study pages by reusing existing components,
spacing, fonts, colours, cards, animations, and responsive
conventions. - Add functional form handling, validation, success/error
messages, analytics, and SEO metadata while retaining the current
design. - Fix bugs, accessibility problems, broken links, and responsive
issues without changing the visual design system.

Before changing code: 1. Inspect the entire existing codebase and
current deployed website. 2. Identify the framework, routing, shared
layout components, styling system, animations, cards, forms, SEO setup,
deployment configuration, and all current page content. 3. Produce a
short implementation map internally or in the final completion summary.
4. Reuse existing components and styles. Do not rebuild the site from
scratch. 5. Preserve the existing appearance with before/after visual
checks at desktop, tablet, and mobile sizes. 6. Do not remove working
content or functionality unless it conflicts with the new positioning or
is broken.

If a requirement conflicts with the current design, preserve the design
and solve the issue through content, component reuse, or minimal
functional changes.

============================================================

performance.

Requirements: - Keep pages fast on mobile networks. - Optimize images
using appropriate formats and dimensions. - Avoid loading large images
or video before needed. - Lazy-load below-the-fold media when

and 1440px. - Prevent horizontal scrolling. - Avoid clipped headings and
overflowing cards. - Keep the existing card layout and responsive design
unless fixing a bug requires a minimal change.

============================================================ 17.
SECURITY AND FORM ABUSE PREVENTION
============================================================

-   Keep API keys and service secrets on the server side.
-   Use environment variables for all secrets.
-   Do not commit .env files containing secrets.
-   Add a safe .env.example with placeholder variable names only.
-   Validate and sanitize all submitted fields.
-   Apply appropriate rate limiting or anti-spam controls.
-   Do not render user input as raw HTML.
-   Avoid exposing internal error details to visitors.
-   Keep dependencies maintained and remove unused dependencies only
    after checking impact.
-   Do not store confidential uploaded files publicly.
-   If file uploads are introduced, define allowed file types, size
    limits, storage permissions, retention, and malware-handling
    requirements.
-   Prefer not to add file upload initially; ask the visitor to describe
    the requirement first.
-   Do not ask visitors to upload payroll, customer, health, payment, or
    other sensitive data through a generic form.
-   If the project later requires sensitive data, agree on a secure
    transfer method separately.
